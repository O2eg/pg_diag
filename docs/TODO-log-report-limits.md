# TODO: глубина, время формирования и размер отчёта по логам

Обновлено 05.10.2026 на исходниках pg-diag 0.18.1 с локальной
доработкой отображения периода и покрытия логов в шапке HTML.
Изменения реализованы и проверены в рабочем дереве проекта.
Уточнение требования: 128 МиБ — мягкий лимит накопленных значений
логовых данных в памяти, а не ограничение размера сериализованного JSON.

## Что есть сейчас

| Ограничение | Текущее значение | Где задано |
| --- | --- | --- |
| Максимальная глубина логов | 10080 минут, 7 суток; по умолчанию 10 минут | `src/pg_diag/logscan/model.py`: `DEPTH_MAX_MINUTES`, `DEPTH_DEFAULT_MINUTES` |
| Общий дедлайн режима `logs` | 300 секунд | `src/pg_diag/logscan/model.py`: `LOGS_REPORT_WALLCLOCK_SECONDS`; `src/pg_diag/logs.py` |
| Таймаут фазы сбора логов | В `logs` — оставшееся время за вычетом 30 секунд на завершение; в `one-shot`/`snapshots` — 60 секунд | `src/pg_diag/logscan/phase.py` |
| Объём возвращаемых сборщиком данных | 128 МиБ, 134217728 байт | `src/pg_diag/logscan/model.py`: `WIRE_BUDGET_BYTES` |
| Объём сканируемых данных | 512 МиБ | `src/pg_diag/logscan/model.py`: `SCAN_BUDGET_BYTES` |
| Объём накопленных значений логовых данных в памяти | Мягкий предел 128 МиБ | `src/pg_diag/logscan/budget.py`; `REPORT_VALUE_BUDGET_BYTES` в `model.py` |

`WIRE_BUDGET_BYTES` применяется до сохранения очередной серии записей
в `LocalLogSource._emit`; удалённый сборщик также получает этот бюджет.
Это ограничение данных сбора, а не объёма значений в объекте отчёта:
таблицы, графики, планы, SQL и метаданные формируются позднее.
`write_json` сериализует объект и записывает его без отдельной проверки размера.
Жёсткий предел размера JSON-файла или JSON внутри HTML не требуется.
Оценка относится к строковым значениям реально сохранённых таблиц, точек
графиков и связанных SQL/планов итогового словаря. `sys.getsizeof(str)` учитывает
представление строки в памяти Python; сериализация и UTF-8-копии не нужны.
Общие объекты строк учитываются один раз по идентичности объекта; отдельные
равные строки учитываются отдельно. Ключи, контейнеры, метаданные представления,
промежуточные LogRecord и нелоговые разделы в бюджет не входят.
Отбор выполняется после ранжирования данных источником: вытесненные планы и
SQL без ссылок из сохранённых результатов бюджет не расходуют. Счётчик
обновляется при сохранении целой строки/точки вместе с её зависимостями.
После пересечения порога оставшиеся логовые элементы явно пропускаются,
а отчёт достраивается. Счётчики отображённых/опущенных записей корректируются.
В конце выполняется один обход сохранённых значений после нормализации типов.
В покрытии сохраняются `estimated_value_bytes`, `value_budget_bytes`,
`value_budget_method: python_string_objects` и причина `report_value_limit_hit`.
`parsed_records` и временные границы описывают фактически разобранное окно;
ограничение выходного словаря не сокращает эти показатели задним числом.
Блокирующие подготовка, чтение, разбор, построение каталога SQL и финализация
выполняются в прерываемых процессах;
передача их результатов также допускает отмену. На завершение и остановку
рабочих процессов зарезервировано время внутри общего дедлайна.
Идентификатор SQL без текста не помечает значение как уже учтённое:
первый фактически сохранённый текст расходует бюджет при его появлении.
Временные файлы JSON/HTML имеют уникальные имена текущего запуска;
после принудительной остановки записи отдельный управляемый процесс удаляет их,
не затрагивая предыдущий отчёт и временные файлы других запусков.
Удаление также ограничено оставшимся временем общего дедлайна.
Локальный и SSH-сборщики одинаково учитывают служебные кадры в бюджете
передачи и останавливаются на одной границе записей. `scanned_bytes`
считает обработанные байты без опережающего чтения транспортного буфера.

  Согласовать таймаут фазы сбора, локальные дедлайны, удалённый harvester
  и SSH с общим дедлайном; предусмотреть время на завершение и запись.
  Простая замена `PHASE_WALLCLOCK_SECONDS` не ограничивает весь процесс.
- [x] Сохранить штатный бюджет возвращаемых данных **128 МиБ**.
  Не переносить в пакет временное увеличение до 1 ГиБ из внешнего
  скрипта `podolsk_2_oct/report/run_report.py`.
- [x] Добавить **мягкий лимит 128 МиБ (134217728 байт)** для накопленных
  значений логовых данных в памяти. Для этой задачи «128 МБ» означает
  тот же двоичный объём, который уже используется в `WIRE_BUDGET_BYTES`.
  Ограничение относится только к данным логов, в том числе в составе
  `one-shot`/`snapshots`; остальные разделы отчёта не расходуют этот бюджет.
  Считать объём приблизительно и постепенно при добавлении данных:
  суммировать `sys.getsizeof()` сохранённых строковых объектов,
  без имён ключей, накладных расходов контейнеров Python, структуры JSON,
  служебных метаданных и ресурсов HTML. Общие тексты SQL/планов из логов
  учитывать по сохранённым значениям, без повторного учёта их содержимого
  при каждой ссылке. Полная сериализация отчёта для подсчёта не нужна.
  После достижения порога прекратить добавление новых логовых данных;
  последнюю добавленную запись и связанные с ней значения сохранить целиком,
  поэтому допускается небольшое превышение. Достроить и сохранить отчёт
  с уже накопленными данными, метаданными и согласованными SQL/plan-ссылками.
  Достижение мягкого лимита само по себе не является ошибкой формирования
  отчёта; размер готовых JSON/HTML может превышать 128 МиБ.
- [x] При достижении мягкого лимита отметить неполноту логовых данных в
  артефакте и показать **красный дисклеймер сразу под шапкой HTML**:
  «В ходе наполнения отчёта был достигнут лимит; отчёт содержит неполные данные».
  Предупреждение должно сохраняться при последующем рендеринге из JSON.

## Критерии проверки

- [x] Глубина 10080 минут принимается; 10081 отклоняется. Фактическое окно
  соответствует запрошенному периоду, а неполное покрытие явно отмечается.
- [x] Общий дедлайн 300 секунд действует и на сбор, и на последующие этапы;
  превышение завершает работу предсказуемо, без продолжения фонового сбора.
- [x] Бюджет сбора остаётся 128 МиБ в локальном и удалённом режимах;
  его достижение отражается в `return_limit_hit` и неполном покрытии.
- [x] Проверено накопление значений ниже порога, ровно на пороге и при его
  пересечении последней целой записью, включая многобайтовые строки.
  Имена ключей, метаданные и нелоговые данные не расходуют мягкий бюджет;
  ссылки на общий текст не приводят к повторному учёту его содержимого.
- [x] При достижении мягкого лимита новые логовые данные не добавляются,
  отчёт успешно достраивается в режимах `json`, `html` и `html,json`;
  усечённые результаты и пропущенные элементы явно отмечены, HTML — красный дисклеймер
  под шапкой. Рендеринг сохранённого JSON воспроизводит предупреждение.
  Без достижения лимита этот дисклеймер отсутствует.
- [x] Сохранены существующие проверки схемы артефакта, SQL/plan-ссылок
  и отображения запрошенного периода и фактического покрытия в HTML.
